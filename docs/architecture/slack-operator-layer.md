# Slack Operator Layer

## Purpose

The Slack layer is an orchestration and observability boundary for operator workflows.

It does not change mission DAG behavior, runtime transition semantics, or controller truth.

## Runtime Flow

1. `runtime/slack/slack-gateway.ts` validates startup config and starts Socket Mode.
2. `runtime/slack/slack-events.ts` handles `/mission`, `/artifact`, and artifact action callbacks.
3. `runtime/slack/slack-router.ts` parses command args and calls `runtime/mission/mission-controller.ts`.
4. Mission controller delegates to existing `control-plane/operator` services.

## Startup Readiness Contract

Gateway startup enforces:

- `SLACK_BOT_TOKEN` required.
- `SLACK_SIGNING_SECRET` required.
- `SLACK_APP_TOKEN` required when Socket Mode is enabled.
- Command handlers must be registered.
- Socket Mode start must complete before ready.

Deterministic startup logs:

- `[Slack] Connected via Socket Mode`
- `[Slack] Commands registered`
- `[Slack] Gateway ready`

## Command Surface

Supported command paths:

- `/mission run <mission>`
- `/mission status <id>`
- `/mission list`
- `/mission logs <id>`
- `/artifact <missionId>`
- `/mission help`

`/mission help` is always available from a pure formatter path.

## Notifications

Slack progress formatting is pure (`runtime/slack/slack-progress.ts`) and observational only:

- `mission_started`
- `step_started`
- `step_completed`
- `mission_completed`
- `mission_failed`

Completion summaries are generated by `runtime/slack/slack-run-summary.ts`.
Failures are operator-safe and include short structured failure detail without stack traces.

## Artifact UX

Artifacts are listed deterministically and rendered with retrieval buttons.
Artifact action callbacks trigger upload transport through `runtime/slack/slack-client.ts`.

Supported upload extensions:

- `.csv`
- `.xlsx`
- `.json`
- `.md`
- `.markdown`
