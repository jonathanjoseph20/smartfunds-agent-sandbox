# Trigger Monitoring Runbook

## Overview

The trigger layer converts deterministic signals into deterministic mission launch requests and stores append-only trigger history.

Trigger behavior is passive:

- triggers request missions
- scheduler remains execution authority
- trigger failures must not break signal emission or runtime launch processing

## Log Locations

Trigger logs are stored at:

- `triggers/YYYY-MM-DD/trigger-log.json`

Signal logs remain at:

- `signals/YYYY-MM-DD/signal-log.json`

## Operator Commands

List active trigger definitions:

```bash
npm run triggers:list
```

Inspect one trigger definition:

```bash
npm run triggers:inspect -- liquidity-drain-investigation
```

View grouped trigger history:

```bash
npm run triggers:history
```

## Diagnosing Duplicate Prevention

Trigger dedupe key is the tuple:

- `triggerId`
- `signalReference`
- `slot`

If a launch request is missing:

1. Confirm matching signal exists in `signals/YYYY-MM-DD/signal-log.json`.
2. Confirm trigger definition exists and `signalType` matches.
3. Check trigger history for the same tuple.
4. If tuple already exists, duplicate prevention is working as designed.

## Mission Launch Request Inspection

Mission launch requests are generated by `trigger-engine.evaluateSignalForTriggers(signal)`.

Result values:

- `triggered`: one or more launch requests created
- `duplicate`: matching trigger definitions found but all suppressed by dedupe
- `no_match`: no trigger definitions for signal type

## Recovery Notes

If trigger evaluation throws:

- signal persistence still succeeds
- runtime launch outcomes are unchanged
- issue can be diagnosed independently via trigger CLI and tests

## Sprint Boundaries

Out of scope for this layer:

- Slack alerts
- dashboard automation
- swarm orchestration
- AI decision logic
- autonomous multi-step workflows
